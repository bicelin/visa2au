# EmDash assessment — can the Visa2AU site be orchestrated via EmDash?

Written after inspecting the live repo, the Cloudflare account, and EmDash's own
documentation. Nothing was migrated. This is an analysis and a recommendation.

**Verdict: technically yes, but not by replacing the current architecture. EmDash cannot be
dropped in "gently" — it is a server-rendering CMS and this site is committed static HTML.
The viable path is EmDash as a headless content backend feeding the existing Python
pipeline (Option B), not an EmDash rendering migration (Option C).**

---

## 1. Assumption check: nothing EmDash is deployed

The recollection was that something CMS-ish already runs in Cloudflare. Measured:

| Resource | Found | Verdict |
|---|---|---|
| Pages projects | `astra-staging` only (serves visa2.au, www.visa2.au, staging.visa2.au) | The site itself |
| Workers | `visa2au-os-workshop`, `-custom`, `-context`, `-errors`, `orange-bonus-6e87`, `holy-wave-47cd`, `allowlistworker-sv`, `report-uri` | None is a CMS; the `os-*` set is a separate product |
| D1 | `visa2au-db` — tables `submissions` (6 rows), `submission_files` (0 rows) | **An enquiry store, not a CMS.** API metadata reported `num_tables: 0`; querying `sqlite_master` showed otherwise |
| R2 | `v2au-agora-rec`, `visa2au-enquiries`, `visa2au-files`, `visa2au-logs`, `visa2au-os-workshop-blueprint-content`, `voice-transcripts` | No EmDash media bucket |
| KV | 3 namespaces, all `visa2au-os-*` | No EmDash session/cache store |

**No EmDash deployment exists in this account** — no Worker, no Pages project, no D1 schema
matching EmDash's tables. If EmDash was deployed before, it was in a different Cloudflare
account or another provider; that would need checking there.

The `visa2au-db` + `visa2au-files` pair (both created 2026-05-27) is the closest thing to a
prior CMS attempt, but the schema is an enquiry form, and EmDash would need its own tables.
Reusing that database would put enquiry data and CMS content in one store — workable, but
worth a deliberate decision rather than a default.

## 2. What the site actually is (measured, not assumed)

| Measure | Value |
|---|---|
| HTML pages | 155 (152 in sitemap; `agoda` is noindex) |
| Generated from `cms/` | **42** (14 posts × EN/RU/FR) |
| Hand-authored HTML | **127 pages, 5.76 MB, avg 45 KB each** |
| Visa pages | 19 per locale × 3 = **57** |
| Distinct structural shapes across the 19 EN visa pages | **3** — 16 pages share one shape, 2 share another, `partner-visa` is richer (14 vs 6 headings) |
| Inline scripts hashed into CSP | 31 |
| Locale strategy | separate HTML per locale, generated by exact-string maps in `scripts/loc/B_{ru,fr}.py` |

So the site is **5.76 MB of bespoke, hand-authored HTML with a bespoke Python build
pipeline**, not a templated framework site. That number is the single most important fact
for this decision.

The 16-of-19 shape result is the good news: the visa pages are effectively one template
with per-page content, so they genuinely can be modelled as a collection.

## 3. What EmDash actually is (from its docs)

- **An Astro integration.** You add `emdash({ database })` to `astro.config.mjs`.
- **Server-rendered.** Its getting-started says it "enables server rendering and the Node.js
  adapter", and that reloading a page "reads the published version from EmDash at runtime"
  via Astro Live Content Collections. The configuration reference is entirely runtime-shaped:
  DB binding, runtime migrations, object cache, route caching, media endpoint.
- **Content in the database**, model editable from the admin or a seed JSON file. 17 field
  types: `string text url number integer boolean datetime select multiSelect portableText
  image file reference json slug repeater blocks`.
- **i18n is strong and matches this site's need.** Row-per-locale entries linked by
  `translation_group`, per-locale slugs, per-locale publish status and revisions, Astro-driven
  routing, and automatic `hreflang` alternates plus a multilingual sitemap. A field marked
  `translatable: false` stays synchronised across all translations — ideal for things like
  visa subclass numbers and prices.
- **Rich text is Portable Text (structured JSON)**, not HTML.
- **Agent-friendly**: CLI, REST API, and a built-in MCP server; `emdash types` can read a
  schema from a *remote* instance (`EMDASH_URL`), which is what makes a headless setup
  realistic.

I found no documented static-output mode. EmDash expects to render.

## 4. The core mismatch

```
TODAY                                  EMDASH
─────                                  ──────
editor → content file                  editor → admin UI → D1 row
   ↓                                      ↓
Python build → static HTML in git      Astro SSR → HTML per request
   ↓                                      ↓
Cloudflare Pages (files, no runtime)   Cloudflare Workers + D1 + R2 (always on)
```

Consequences that make "gently plug it in" impossible:

1. **The guarantees this site won for itself are file-based.** `check_seo_invariants.py`
   (`OK: 152 pages, canonicals/hreflang/sitemap consistent`), `audit_link_graph.py`
   (`0 dead, 0 EN-fallback-with-twin`), and `update_csp_hashes.py` (31 hashes, no
   `unsafe-inline`) all inspect committed HTML. EmDash rendering bypasses every one of them.
2. **Locale handling is implemented twice, differently.** Today RU/FR are generated by
   exact-string translation maps applied to English HTML. EmDash uses row-per-locale
   entries. Adopting EmDash means either abandoning the maps or maintaining both.
3. **The CSP would change shape.** EmDash injects admin assets, a media endpoint, and its own
   head management. The current no-`unsafe-inline` posture would need re-deriving.
4. **The Stripe endpoints live in `functions/api/`** as Pages Functions (`checkout.ts`,
   `donate.ts`, `verify-payment.ts`, `stripe-webhook.ts`). An Astro migration turns those
   into Astro API routes — including the webhook that is currently one `whsec_` away from
   done.

None of that makes EmDash wrong. It makes it a **different architecture**, and the migration
is a presentation-layer rewrite, not a plugin install.

## 5. The content model EmDash would need (derived from the real pages)

This is the reusable part: it is valid whether you pick Option B or C. Field types are
EmDash's own.

### `visas` — 19 entries × 3 locales

Derived from the shared shape of the 16 identical pages.

| Field | Type | Notes |
|---|---|---|
| `title` | `string` | e.g. "Parent Visas"; required |
| `subclass_code` | `string` | `103`, `143`, `870`; `translatable: false` |
| `lede` | `text` | intro paragraph |
| `overview` | `portableText` | the "Overview" section |
| `journey_steps` | `repeater` | **4 items** — `title` + `description`, the "Your journey with Visa2AU" block |
| `eligibility` | `portableText` | the "Eligibility requirements" list |
| `documents` | `portableText` | the "Document checklist" list |
| `faq` | `repeater` | `question` + `answer` — powers the FAQPage JSON-LD |
| `at_a_glance` | `repeater` | `label` + `value` — the existing `<dl>` ("Processing time" → "…", "Government charges" → "…") |
| `related` | `reference` → `visas`, multiple | the "Related pathways" block |
| `hero_image` | `image` | |
| `seo_title` | `string` | `validation.maxLength` — the SEO gate enforces title limits, so encode it |
| `seo_description` | `string` | `validation.maxLength` likewise |

Note the JSON-LD currently emitted per visa page (`LegalService`, 3 blocks) is derived, so it
must be regenerated from fields, not edited by hand.

### `blog_posts` — 14 × 3, existing content
Already modelled in `.pages.yml`; maps almost 1:1: `title string`, `slug`, `date`, `category
select`, `description`, `excerpt`, `author reference → authors`, `image image`,
`reading_time integer`, `body portableText`. `lang` becomes the locale, not a field.

### Supporting collections

- **`authors`** — `name`, `marn`, `bio`, `photo` (reference target for bylines).
- **`fees`** — for `/pricing`, the fee hub: `service string`, `amount number`
  (`translatable: false`), `notes`, `category select`. Today these amounts are prose in HTML.
- **`pages`** — home/pricing/contact/about/pay/donate chrome: mostly `blocks` composition,
  but `pay` and `donate` should **stay as code**, since their copy is contractually tied to
  Stripe behaviour (test vs live wording, the A$30,000 cap message, the "do not pay twice"
  warning). Making those editable invites a repeat of the "test mode while charging real
  cards" hazard.
- **Taxonomies** — blog `category` maps to an EmDash taxonomy (10 categories already listed
  in `.pages.yml`).

### Fields that must NOT become editable
`subclass_code`, prices, legal disclaimers, the Stripe cap messages, MARN numbers. Use
`translatable: false` and/or keep them in code. The site's correctness depends on those
facts being identical everywhere.

## 6. Options

### Option A — keep Pages CMS (status quo)
- **Effort:** none. **Risk:** none.
- Blog editing only. The 127 hand-authored pages remain developer/agent territory.
- Honest read: this is sufficient if the only goal is "Natasha can write blog posts".

### Option B — EmDash as a headless backend, static site unchanged ⭐ recommended
EmDash runs on Workers + D1 + R2 as an **editor-facing** system. The public site never talks
to it: a build step pulls content via the REST API / CLI / MCP and feeds the existing Python
pipeline, which keeps emitting committed static HTML.

- **Keeps:** every current invariant (SEO gates, CSP hashes, link graph, locale maps), the
  static security posture, zero runtime cost per visitor, and the Stripe Functions as-is.
- **Gains:** real structured editing, per-locale publishing with proper `translation_group`,
  revision history, media library, and MCP/CLI so agents can drive content.
- **Costs:** you write and own a one-way sync layer; EmDash's visual editing and Live
  Collections go unused (its admin is then just a content editor); two systems to operate;
  content edits require a rebuild to appear.
- **Risk:** low to the live site — if EmDash falls over, visitors are unaffected; only
  editing stops.
- **Highest-value first target:** `visas` (16 near-identical pages), then `fees`, leaving
  blog on Pages CMS until the sync is proven.

### Option C — full EmDash migration (site becomes Astro SSR on Workers)
- **Effort:** large. 155 pages → Astro routes; re-implement or retire the Python gates; port
  the Stripe Functions to Astro API routes; re-derive the CSP.
- **Gains:** one coherent system; EmDash owns i18n, hreflang and multilingual sitemaps;
  live/visual editing; plugin ecosystem.
- **Costs:** the 5.76 MB of hand-authored markup has to be re-expressed as templates and
  Portable Text; the SEO guarantees must be rebuilt or replaced; everything becomes a
  runtime dependency.
- **Risk:** high, and concentrated exactly where the site has already been hurt before —
  SEO consistency, hreflang correctness, and CSP integrity. This is the option most likely
  to silently regress something that currently passes a gate.

---

## 7. Recommended sequence (if Option B)

1. **Decide the database.** A dedicated D1 for EmDash; leave `visa2au-db` as the enquiry
   store. D1 free tier covers this comfortably.
2. **Stand EmDash up in isolation** — own Worker, own D1, `staging`-only, not linked to
   `visa2au` traffic. Prove admin, passkey auth, and i18n with EN/RU/FR.
3. **Model `visas` only** (the schema in §5) plus `authors`. Do not touch the blog.
4. **Write the sync**: EmDash REST → JSON in the repo → `build_visa_pages.py` → existing
   pipeline → existing gates. The gates are the safety net; if they stay green, the change
   is safe.
5. **Prove parity on one visa page** before touching the other 15, and diff the rendered
   HTML against today's to confirm identical structure and meta.
6. Only then widen to all 19, then consider `fees`, then decide whether the blog moves.

Rollback at every step is `git revert` on the generated HTML plus deleting the Worker — the
public site keeps serving statically throughout.

---

## 8. What I could not verify

- Whether EmDash supports a purely static build. Not documented in what I read, and its
  setup enables SSR, so Option B assumes content is pulled via its API rather than by Astro
  rendering. **Worth confirming before committing to B**, since if a static build *is*
  supported, B becomes considerably cleaner.
- Whether the Pages CMS GitHub App is installed, i.e. whether the current blog CMS actually
  opens in a browser.
- Whether an EmDash instance exists in another Cloudflare account or on another provider.

## 9. Bottom line

EmDash is a genuinely good fit for the *content* problem here — its row-per-locale i18n,
`translatable: false` fields, repeaters for the `<dl>`/FAQ/checklist blocks, and MCP/CLI
access map onto this site's real structures unusually well. The visa pages in particular are
a clean collection waiting to happen.

It is a poor fit for a *gentle* migration, because adopting its rendering model means
rebuilding the presentation layer and giving up the file-based gates that currently keep the
SEO and CSP work honest. Take the content model, keep the static pipeline.

## 10. Phase 1 results (Option B, executed locally)

A local EmDash instance was built at `~/Projects/kimi/workspace/v2au-emdash` (Node adapter,
SQLite). **The live site was never touched** — nothing was deployed to Cloudflare.

### Confirmed

| Question | Result |
|---|---|
| Does EmDash have a static build mode? | **No.** The scaffold writes `output: "server"` with an adapter. This settles §8's open question and confirms Option B's design (pull via API, don't adopt rendering). |
| Can content be managed without a browser/passkey? | **Yes for model + content.** `emdash init` (98 migrations), `seed --validate`, `seed` all run headlessly. Only the admin *login* needs a passkey. |
| Does the derived `visas` model validate? | **Yes** — "Seed file is valid" against EmDash's own schema validator. 1 collection, 12 fields, 19 entries created. |
| Does content store as designed? | **Yes.** `ec_visas` has typed columns (`title TEXT`, `subclass_code TEXT`) plus `json` columns for `journey_steps`, `eligibility`, `documents`, `faq`, `at_a_glance`, `related`, and system `locale` / `translation_group` for i18n. |
| Is extraction faithful? | **Yes.** `parent-visa-103` round-trips: title "Parent Visas", subclass `103`, journey 4, eligibility 5, documents 5, faq 1, at_a_glance 3 (exact `Processing time` / `Government charges` / `Our professional fee` pairs), related 3. |

### Extraction coverage

`scripts/emdash_export_visas.py` exports all 19 visa pages: **18 extract cleanly**;
`partner-visa` is the outlier (10 FAQs but no journey/eligibility/glance blocks) because it
is the richer hub page with 14 headings rather than 6. It needs its own shape decision —
either a `blocks` composition or an accepted null-payload subgroup.

### Environment finding (matters for CI and for Sergey's machine)

EmDash requires **Node ≥ 22.23.4**. This machine has `node@22` at **22.23.2** — two patches
short — while Homebrew's stable `node@22` is 22.23.5. The PoC ran on Node 26.12.1 from
`~/.hermes/tools/`. Any CI workflow for EmDash must pin a compliant Node explicitly.

### Remaining before a real deployment

1. **One-time human setup**: complete the wizard at `/_emdash/admin` and register a passkey
   (cannot be automated — WebAuthn).
2. **Sync credentials**: the content API returns `401 NOT_AUTHENTICATED`; `emdash login`
   accepts `--url` and repeatable `--header`. The build job needs a bearer token issued from
   the admin, stored as a secret.
3. **Then**: EmDash REST → JSON → `build_visa_pages.py` → existing pipeline → existing gates,
   with a byte-level parity diff on one page before widening.

## 11. Phase 2 results — deployed to Cloudflare

EmDash now runs in the Cloudflare account, fully isolated from production.

**Live at `https://v2au-emdash.bicelin.workers.dev`** (`/` = 200, `/_emdash/admin/` = 302 to setup).

### Resources created

| Resource | Name / id | Notes |
|---|---|---|
| Worker | `v2au-emdash` | Durable Object class `EmDashRoom` created on deploy; startup 39 ms |
| D1 | `v2au-emdash-db` · `23f92398-b2ac-4874-a5e2-61a340313d6c` | region OC; separate from the `visa2au-db` enquiry store |
| R2 | `v2au-emdash-media` | media storage |
| KV | `SESSION` (auto-provisioned) | session store, created by wrangler during deploy |
| Images | `IMAGES` (auto) | Cloudflare Images binding |

**Production was not touched:** `visa2.au/`, `/pay`, `/donate` all still 200. The Worker has
no custom domain and no route — it is reachable only at its `workers.dev` hostname.

### Content is in the remote database

Verified by querying D1 directly: **19 visas, 19 revisions, 18 fields, 94 tables.**

Two details worth knowing:

1. **`ec_visas` is a dynamic table.** Copying rows failed at first with
   `no such table: ec_visas` and then a `FOREIGN KEY constraint failed` — each collection
   gets a real SQL table created when the collection is defined, not by core migrations, and
   `ec_visas.live_revision_id` references `revisions`. Import order is therefore
   **collections → fields → ec_visas DDL + FTS triggers → revisions → content**. Any future
   import must respect that order.
2. **The Worker auto-applied the starter seed.** `package.json` declares
   `emdash.seed = seed/seed.json`, so on first boot the deployed instance created the
   template's `posts` and `pages` collections (6 extra fields). Those are demo scaffolding
   and should be removed once the real model replaces them.

### Still open

- **Admin setup (passkey)** — cannot be automated; `/ _emdash/admin/` redirects to the
  wizard. Required before an API token can be issued.
- **Sync credentials** — the content API still returns `401 NOT_AUTHENTICATED`.
- **Routes are irrelevant under Option B** — `/visas/parent-visa-103` 404s because the
  starter template has no visas route. That is expected and fine: the site keeps rendering
  its own HTML; only the API is consumed.
- **The every-minute cron** (`* * * * *`) is EmDash's maintenance scheduler. Harmless at
  1,440 invocations/day, but worth an explicit decision rather than inheriting it.
